Here's the full picture of how it works end-to-end, from raw data to a working model, and how you'd judge if it's good — specific to Recommendations AI (Retail API / Vertex AI Search for commerce).

## 1. What data Google ingests, per company

Every company gets its own **isolated project and catalog** — models are trained only on that company's data, never mixed with other customers' data. Two data streams feed the model:

**Product catalog**
- Core fields: product ID, title, category hierarchy, description, price, availability, images/URLs
- Besides product ID, title, category hierarchy, and price, URLs are considered one of the primary fields used as inputs for model training.
- **Custom attributes** — this is where it gets company-specific. Retailers can add up to thousands of their own product attributes (material, brand, size, style tags, etc.), and the system goes through all custom attributes for each retailer and chooses the most useful ones to add to the set of static product features, repeating this feature selection process roughly every 30 days. So a fashion retailer's model might end up weighting "fabric type" or "fit," while a hardware retailer's model weights "voltage" or "material grade" — Google auto-detects what's predictive for *your* catalog specifically.
- The catalog should be kept up to date, ideally imported daily, since letting it go stale degrades model quality over time.

**User events**
- Event types: homepage views, detail-page views, add-to-cart, purchase-complete, category-page-view, etc.
- From these events, the system determines which products were clicked, added to cart, and purchased, and this data both trains the model as it gets more interaction and conversions and forms the basis for KPI measurement like revenue per user, CTR, and CVR.
- To train against historical behavior, past site-engagement data typically needs to be backfilled and transformed into the prescribed event schema before continuous real-time events take over.
- Some models require ingesting user event data for 60–90 days before they can even be trained.

## 2. What the model actually considers

For a given company, the model combines:
- **Product-side features**: category, price, availability, plus the auto-selected custom attributes relevant to that catalog
- **Behavioral signals**: each user's sequence of views/clicks/cart-adds/purchases
- **Context**: page type, timestamp, device, filter tags
- **Business rules layered on top**: you can manually boost/bury certain products, diversify results, or filter by tags/availability without retraining the model

Each model type (Others You May Like, Frequently Bought Together, Recommended for You, etc.) is trained toward one of **three optimization objectives**:
- **Click-through rate** — maximize likelihood of a click
- **Conversion rate** — maximize likelihood of purchase
- **Revenue per session** — maximize expected revenue

This objective is chosen at training time and can't be changed after — you'd retrain a new model for a different objective.

Daily model retraining ensures the models stay accurate as new catalog and event data comes in.

## 3. How to evaluate it (tying together what we discussed before)

**A. Data quality gate first** — before judging the model at all, check the Data Quality dashboard. It's structured in 4 cumulative tiers, where data requirements are classified as Compliant, Performance Critical, or Upgrade Blocking for each tier. You need to clear these tiers, or any "evaluation" you do is really just measuring data gaps.

**B. Model-side metrics**: Recall@K, NDCG, diversity, coverage (as discussed earlier).

**C. Business metrics**: CTR, conversion rate, revenue per recommendation — all derivable from the user events you're already sending, since user events are the basis for KPI measurement including revenue per user, CTR, and CVR.

**D. Attribution tokens** — a detail specific to this product worth knowing: attribution tokens enable performance metrics for recorded user events by capturing first-time user interactions with a product based on previously provided recommendations or search results. Without correctly threading the attribution token from a `predict` response into the follow-up click/purchase event, Google's own dashboard can't tell you which conversions came from recommendations vs. organic browsing — this is the single most common setup mistake that makes "the model isn't working" look true when it's actually a plumbing issue.

**E. A/B testing** — the real verdict. Tag traffic with `experimentIds` in the predict request and compare a recommendation-served group against a control (e.g., "most popular" fallback or no personalization), only once the model is at Tier 3 data quality.
